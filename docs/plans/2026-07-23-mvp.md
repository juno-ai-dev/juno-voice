# Juno Voice MVP implementation plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Ship and live-smoke a Juno Voice CosmWasm contract plus a Juno Design System-compliant web client for requests, fixed-snapshot voting, lifecycle history, and delivery evidence.

**Architecture:** A single Rust contract owns canonical records and queries Juno `x/voting-snapshot` through custom bindings. A TypeScript client reads RPC directly for detail and may use a derived indexer for search. The first implementation stays non-binding and excludes arbitrary execution, payouts, and comments.

**Tech stack:** Rust/CosmWasm, `cw-storage-plus`, CW2, Juno custom query bindings, TypeScript, React-based framework selected after inspecting current Juno app precedent, CosmJS, Juno Design System.

---

## Architecture basis (accepted; not an implementation pause)

Implementation follows the accepted canonical architecture and ADRs:

- `docs/architecture/decisions/001-fixed-snapshot-power.md`
- `docs/architecture/decisions/002-non-binding-prioritization.md`
- `docs/architecture/decisions/003-chain-canonical-index-derived.md`
- `docs/architecture/decisions/004-lifecycle-and-bonds.md`
- `docs/architecture/decisions/005-authority-evidence-attestation.md`
- `docs/architecture/decisions/006-ranking-schema-recovery.md`

Implementation uses the launch defaults in canonical `ARCHITECTURE.md`: 10 JUNO bond, 432,000-block voting and inactivity windows, 50 bps quorum, 5,001 bps support, `uni-7` exact-artifact smoke, `juno-1` production target, the documented Juno Agents DAO/Juno agent role profile, and a pinned Juno Design System source subtree. These remain explicit instantiate/deployment inputs and must be revalidated against live chain state before use. Do not deploy or accept funds until chain-admin custody, exact values, and retention assumptions are disclosed. Migration/upgrade policy and rehearsal are launch concerns and do not gate MVP implementation.
